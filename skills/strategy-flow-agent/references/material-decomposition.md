# Material decomposition

把材料拆成“证据 → 事实候选 → 待确认问题”。先让 CLI 生成 corpus，再基于 corpus 分析；不要绕过 parser 手写一份 corpus。

## 支持的材料类型

| 类型 | 通常提供的信号 | 注意事项 |
|---|---|---|
| `.docx` | 需求叙述、标题层级、段落、表格 | 表格优先承载流程，段落承载业务口径；两者冲突时标 conflict |
| `.xlsx` | 多 sheet、表格行列、状态列、执行人列 | 保留 sheet 名和表头语义；空单元格不是无动作，未说明就标 missing |
| `.pptx` | 页标题、幻灯片文本、页面表格 | 适合方案概述，不一定能推导完整流程；缺执行链时不要补齐 |
| `.csv` | 单表流程、清单、指标 | 注意分隔符、表头重复、中文空格；不要凭列名猜业务状态 |
| `.md` | 标题、段落、列表、表格 | Markdown 示例不是事实；需区分需求、假设和示例 |
| `.txt` | 自由叙述 | 证据密度低，更多字段应保持待确认 |

不支持的文件不要降级解析。请用户转换为上述格式；若转换会导致语义丢失，让业务人员在转换件中补充来源说明，并把转换件作为新文件重新解析。

## 事实抽取清单

### 1. 策略基础信息

识别策略名称、业务单位、负责人、提交人、提交日期、生效日期、核心钩子、基线版本和触发场景。日期只接受材料或人工确认的值；不要用当前日期填充。

### 2. 责任执行人与对象状态

每张流程卡片应拆出：

- 责任执行人：谁处理这张卡片。
- 对象类型：客群、场景、事件、活动。
- 对象名称：该类型下的具体业务对象。
- 对象状态：对象进入卡片时的业务状态，不是处理进度。

材料只写“已处理”“进行中”这类执行进度时，不要直接当对象状态；作为 openQuestion 请业务人员翻译成对象状态。

### 3. 流程节点与流转规则

- 从表格、编号列表、泳道描述中拆节点和先后关系。
- 每条边区分执行人行为和对象行为；两侧都没有要求时才是无动作。
- 条件、阈值、等待时长、失败分支、回收和重入必须引用具体 fragment。
- 材料只有线性顺序而没有条件时，生成待确认问题，不要编 `if/else`。

### 4. 对象分类信号

Design 0.4 用 `nodes[].nodeType = "classification"` 表达“对象分类”卡片。它可作用于客群、场景、事件或活动，表示执行人对对象做分类、分层或重新分层；对象本身无行为要求，也不因此被触达。

**显式信号**：材料同时出现分类 / 分层 / 分群 / 打标 / 按行为划分 / 产出细分对象等意图，并能定位到被分类对象、执行人或分类结果之一。此时可以把“存在对象分类需求”记录为证据支撑的候选意图，并引用具体 `evidenceId`。

**弱信号**：材料只出现“高潜 / 低潜 / 核心 / 长尾”等层级词、多个细分对象名，或只描述差异化策略而没有说明先分类。这些只能形成 openQuestion，请业务人员确认是否存在前置或中间分类动作，不得直接认定为 `classification`。

需要人工确认的缺口：

- 被分类的对象类型和名称：客群、场景、事件或活动。
- 分类执行人 / 角色。
- 分类依据：行为特征、状态差异、阈值、优先级和兜底规则。
- 输出结果：互斥分类 / 分层清单和未分类处理方式。
- 后续承接：统一入口、分支策略或再次分类。
- 过程指标：分类覆盖率、细分重叠率、未分类率、规则命中率等。

落地边界：

- `classification` 是 Design 0.3 引入、0.4 继续使用的能力；0.2 只有 `process`，不得把 0.2 的展示名或动作描述自动猜成新类型。
- 当前离线 stub 生成 Design 0.4，但不会自动生成 `classification`。Agent 发现信号后只能在审查汇报 / openQuestions 中提示，待业务人员确认后在编辑器显式添加或修改卡片。
- 不要直接修改 `strategy-agent-store` 里的 draft 来补 `classification`。
- 分类依据、动作、结果和指标继续挂在 `processActions`；`classification` 禁止挂接 `strategyActions`。
- 所有出边的对象行为必须是 `no_requirement`；执行人变化仍需 `handoff`。

### 5. 策略动作与过程动作

- 客户触达内容：触达场景、触达方式、话术、权益、客户指标。
- 执行跟进动作：跟进执行人、执行内容、过程指标、检查节奏。
- 动作必须挂接到真实节点或边；没有挂接点就列为问题，不要创建空壳节点。

### 6. Taxonomy

- `code` 是唯一持久化稳定值；展示可用 label。
- 多选、单选和父子关系以 `strategy-taxonomy/2026-09` 为准，不要凭材料文案自造 code。
- 新业务场景、策略类型、触达场景或触达方式只能走 `customTagProposals`，包含 `proposalId + label + reason + parentRef`；未审批不得伪装成既有 code。
- 自由文本策略子类放 `strategySubtype`，不要塞进结构化标签。

### 7. Metadata companion

`businessUnit`、`submitDate`、`coreHook`、`effectiveFrom`、`baselineVersion`、`triggerScenes` 属于 Metadata 2.0。标签字段禁止写入 metadata；标签唯一事实源在 Design JSON 的 `taxonomy`。

## 证据账本

为每个候选事实记录：

```text
目标：design:/nodes/0 或 metadata:/submitDate
结论：只写材料可支撑的值
状态：supported / missing / conflict
证据：ev-...（文件名 + ordinal / table / slide）
置信度：仅在协议要求或响应已提供时引用
待办：需要业务人员回答的问题
```

规则：

- `supported` 至少引用一个存在的 `evidenceId`。
- `missing` 不引用证据，候选值保持“待确认”或空。
- `conflict` 至少引用两个互相矛盾的证据，并写明差异。
- 多个文件重复同一事实仍可归并为一个候选，但保留全部 evidenceRefs。
- 术语同义但业务口径不同（例如“流失”与“沉睡”）不要合并；先问业务人员。

## 冲突与缺口处理

1. **证据冲突**：列出两个 evidence 的原文位置和差异，请业务人员选择或改写，不得静默取最新、最详细或第一个。
2. **字段缺失**：给业务人员说明字段用途、可选来源和影响，不给默认业务值。
3. **表格结构歧义**：先问表头和行列语义，再映射节点 / 边 / 动作。
4. **指标只有名称没有口径**：保留名称，口径列为待确认；不要写 SQL、阈值或统计逻辑。
5. **材料存在历史版本**：让用户确认基准版本；不同版本冲突按 conflict 处理。

## 禁止事项

- 不要把 Mermaid 当输入事实源，也不要承诺从 Mermaid 无损恢复 JSON。
- 不要把画布坐标、间距、颜色等布局字段写入业务语义。
- 不要为了凑完整流程添加入口、终态、回收或重入节点。
- 不要把“高潜 / 低潜 / 核心 / 长尾”等层级词直接当成对象分类事实；先确认这些是输入对象、分类结果还是策略命名。
- 不要把通用行业常识当成业务证据。
- 不要把 PDF OCR / 截图文字等未经 parser 的内容伪装成 corpus evidence。
